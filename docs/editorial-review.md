# การเพิ่มคุณค่าและตรวจสอบข่าว

ข่าวใหม่จากระบบจะมี `reviewedBy: null` การสร้างไฟล์หรือการผ่าน automated validation ไม่ใช่การตรวจโดยมนุษย์ หน้าข่าวจะแสดงชื่อผู้ตรวจสอบเมื่อมีทั้ง `reviewedBy` และ `reviewedAt` เท่านั้น ไม่ควรใส่ชื่อทีมอัตโนมัติแทนผู้ตรวจจริง

หลังตรวจบทความแล้ว ให้บันทึกชื่อที่ผู้ตรวจใช้จริงและเวลาที่ตรวจจริง เช่นรูปแบบต่อไปนี้ (เปลี่ยนค่าตัวอย่างก่อนใช้):

```yaml
reviewedBy: "ชื่อผู้ตรวจสอบจริง"
reviewedAt: "2026-10-27T23:00:00+07:00"
references:
  - title: "ชื่อรายงานหรือประกาศต้นทางที่อ่านแล้ว"
    url: "https://example.com/original-report"
    kind: primary
  - title: "เอกสารประกอบที่ใช้ตรวจสอบบริบท"
    url: "https://example.com/context"
    kind: supporting
```

`references` ไม่บังคับสำหรับบทความเดิม ใช้ `primary` สำหรับเอกสารจากผู้ประกาศ ผู้พัฒนา หรือรายงานวิจัยต้นทาง และ `supporting` สำหรับข้อมูลประกอบ ลิงก์อ้างอิงต้องเปิดอ่านและรองรับประเด็นที่เขียน อย่าเติม URL จากการคาดเดา และอย่าเปลี่ยน `sourceUrl` ให้เป็นแหล่งที่ไม่ได้ใช้เรียบเรียงจริง

ก่อนเผยแพร่:

- ตรวจชื่อ รุ่น ตัวเลข วันที่ และเงื่อนไขกับต้นฉบับ แยกคำกล่าวของบริษัทออกจากผลทดสอบอิสระ
- เพิ่มลิงก์เอกสารต้นทางใน `references` และอ้างในย่อหน้าที่เกี่ยวข้องเมื่อมีเอกสารที่ตรวจสอบได้
- ให้บทวิเคราะห์เชื่อมข้อเท็จจริงเฉพาะในข่าวกับผลต่อผู้อ่าน อธิบายว่าควรตรวจสอบอะไรหรือทำอะไรต่อ และมีข้อจำกัดใด
- อย่าเติมราคาเงินบาท ความพร้อมในไทย ผลทดสอบ หรือประสบการณ์ใช้งานที่ไม่มีหลักฐาน ความยาวที่เพิ่มขึ้นอย่างเดียวไม่เพิ่มคุณค่า
- หากยังไม่ยืนยันข้อกล่าวอ้างสำคัญ ให้คงบทความเป็น draft และตรวจสอบก่อนเผยแพร่
- ข่าวเก่าที่มีชื่อทีมจากระบบเดิมต้องตรวจจริงก่อนเพิ่ม `reviewedAt` ไม่เติมย้อนหลังอัตโนมัติ

รัน `pnpm validate:content`, `pnpm test` และ `pnpm build` ก่อนส่งงาน
